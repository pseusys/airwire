# airwire core (Phase 0 proof of concept)

Platform-independent Python implementation of airwire's crypto, message framing, and SMS
chunking, per the [product README](../README.md) and [roadmap](../docs/roadmap.md#phase-0--core-engine-poc-python-no-app).

No mobile code lives here. The point of this package is to prove the protocol design — and, once
it's frozen, to serve as the source of test vectors the future Android/iOS clients get checked
against — before any platform-specific work starts.

## How the steganography works

Two independent disguise mechanisms exist so far — one for text, one for images — and they share
one core trick underneath: an **arithmetic coder** run in reverse. Normally, arithmetic coding
*compresses* a sequence of symbols into fewer bits by spending less on likely symbols and more on
unlikely ones. Run backwards, the same machinery does the opposite: feed it the (already
random-looking) ciphertext bits, and it *expands* them into a sequence of choices, weighted so
"cheap" (likely) choices come up more often than "expensive" (unlikely) ones — which is exactly
the statistical signature of anything that reads as natural, whether that's common words in a
sentence or a smoothly blending patch of texture. Run *forwards* over the resulting output, the
same walk exactly reconstructs which choices were made, and therefore the original bits — with no
floating point, no machine learning, and no randomness anywhere in the path, so two independently
built devices always agree bit-for-bit. `sources/arithmetic.py` is that shared coder;
`sources/markov.py` and `sources/synthesis.py` each just hand it a different notion of "candidate"
and "how much each one should cost."

### Text: a Markov chain read backwards

1. A **frozen Markov chain** is a big lookup table: for every pair of consecutive words seen in a
   real corpus (a "state," e.g. `("the", "cat")`), it records which words tended to come *next*,
   and how often. `sources/corpus.py` downloads real sentences (English and Russian, from
   [Tatoeba](https://tatoeba.org/en/downloads)); `scripts/model.py` builds the table from them and
   freezes it to `sources/data/markov_<language>.json`.
2. To disguise a hyperslice's ciphertext, `sources/markov.py` starts at a "beginning of sentence"
   state and, at each step, looks up that state's candidate next words and their real-world
   frequencies. Those frequencies become the arithmetic coder's weights, and the next few bits of
   ciphertext pick *which* candidate — common words are cheap (cost few bits), rare ones
   expensive, exactly mirroring how the words actually get used in real language.
3. The chosen word shifts the state forward (the two-word window slides by one) and the process
   repeats. A special "end of sentence" marker is just another weighted candidate — choosing it
   resets the walk back to the beginning, which is why the output comes out as several separate
   sentences rather than one long run-on one.
4. The walk stops the instant every ciphertext bit has been spent — no more, no less — because the
   coder is never allowed to ask for more precision than there are real bits left to supply it.
   No length prefix or end marker needs to travel on the wire at all: the receiver already knows
   the target byte count from the (encrypted) hyperchunk header.
5. **Decoding** replays the identical walk forwards through the words that were actually written
   down, using each one to work out exactly which slice of the arithmetic range it must have come
   from, and accumulates the same bits back out — the same arithmetic, run in the same order, so it
   always lands on the exact original ciphertext.

See [design decision #3](../docs/design-decisions.md#3-the-markov-chain-text-disguise-encoding)
for why this was hand-rolled rather than built on an existing entropy-coding library, and its
current limitations (the sentence-boundary marker is a literal `___END__` tag rather than
punctuation; only the English model auto-detects on receive, Russian must be requested explicitly
on both ends).

### Images: texture synthesis, read the same way

1. A **source texture** is a small square image generated by a simple, fully deterministic
   procedural algorithm — `sources/textures.py` currently has four: smooth cloud-like noise,
   stained-glass-like Voronoi cells, a coral-like reaction-diffusion simulation, and a swirling
   chaotic attractor. Each needs nothing but a size and a seed number to regenerate exactly, so
   both ends produce an identical texture independently — no download, no shared file, unlike the
   text corpora.
2. The texture is cut into a library of small square **patches**. The output image is built row by
   row: every *other* row is a **seed row** — real, untouched patches from the source texture,
   placed by a fixed rule that has nothing to do with the secret data, there purely to anchor the
   pattern.
3. The rows in between are **gap rows**, filled one patch at a time. For each empty spot,
   `sources/synthesis.py` scores every patch in the library by how well its edges would blend with
   the (already-known) patches above, below, and to its left — closer pixel values score better.
   Those scores become the arithmetic coder's weights, exactly as word frequencies did for text:
   good matches are cheap, poor matches expensive, and the ciphertext bits pick which patch
   actually lands there.
4. Growth continues row-pair by row-pair until the ciphertext is exhausted; any leftover space in
   the final row is padded with the single best-matching patch, which costs no bits at all — purely
   there to keep the image rectangular.
5. **Decoding** walks the same grid, recomputes the same blend scores from each gap patch's
   already-known neighbors, looks up which patch is actually sitting there, and inverts the
   arithmetic step exactly as the text decoder does.

This is a deliberately simplified adaptation of a real, non-neural 2015 steganography technique
(Wu & Wang's "reversible texture synthesis") — see
[design decision #4](../docs/design-decisions.md#4-image-steganography-patch-based-texture-synthesis-prototype)
for what was changed and why, and an honest account of where it currently falls short: it
round-trips exactly for all four texture styles, but visual quality still varies a lot — smooth
noise-like textures hold up well, while textures with large connected shapes (Voronoi cells,
reaction-diffusion tubes) come out more fragmented than their source, because the blend score only
ever looks at immediate neighboring pixels, with no way to keep a big shape coherent across many
patches.

Each texture flavor *is* a `ChunkEncoding` (`ImageEncoding` in `sources/synthesis.py`), just one
whose `encode_atoms` yields exactly one atom — the whole synthesized image, PNG-encoded — instead
of many small pieces. One atom always fills exactly one wire chunk, so `pack_hyperchunk` produces
`[header, one big chunk]` for an image hyperslice: the "one hyperslice, one image" MMS-attachment
shape, achieved by reusing all of `sources/chunking.py`'s existing header/ack/retry machinery
rather than a second delivery path (just with an MMS-scale `chunk_size` instead of an SMS one) —
see the wire-integration section of design decision #4.

### Disguising the header, and where the disguise choice itself comes from

Both disguises above only ever applied to the *payload* — the hyperchunk header was always sent as
a plain encrypted blob, even in `markov` mode, which meant one raw-binary-looking message sitting
right next to a stream of otherwise-disguised ones. `pack_hyperchunk`'s optional `header_encoding`
parameter fixes that: it pads the header to a fixed size (so its disguised length doesn't need to
be self-describing) and runs it through the same disguise machinery as the payload.

Neither `encoding` nor `header_encoding` are meant to be picked per message, though — see
[`docs/handshake.md`](../docs/handshake.md) for the full design, but in short: each sender's
messages (handshake certificate included) are disguised the same way for the entire conversation,
derived from nothing but that sender's own public transport identifier (a phone number, a platform
user ID), needing no exchange or pre-shared secret at all. `sources/handshake.py` is the
implementation of that document — session establishment (an unsigned, plain-TOFU certificate
exchange plus an X25519-derived session key) and the obfuscation-mode derivation both live there.

## Contents

- `sources/crypto.py` — X25519 key exchange + XChaCha20-Poly1305 AEAD, via
  [PyNaCl](https://pynacl.readthedocs.io/) (libsodium bindings).
- `sources/proto/envelope.proto` — the message format from the [README's table](../README.md#message-format):
  `id`, `sender`, `recipient`, `type`, `payload`.
- `sources/proto/hyperchunk.proto` — the `HyperchunkHeader` and `HyperchunkAck` messages used by
  `sources/chunking.py` below, plus the `ChunkEncoding` enum described next; header and ack are
  both encrypted as a whole before going on the wire. Every disguise variant (each Markov language,
  each texture flavor) gets its own identifier, not just one per family.
- `sources/proto/handshake.proto` — the `Certificate` message used by `sources/handshake.py` below.
- `sources/encodings.py` — pluggable strategies (`ChunkEncoding`) for turning hyperchunk ciphertext
  bytes into the bytes that actually travel in wire chunks: `PlainEncoding` (raw bytes),
  `Base64Encoding` (visible ASCII, a middle ground between raw binary and a fully disguised
  encoding), and (registered by `sources/chunking.py`, to keep this module free of any one
  encoding's own dependencies) the Markov-chain and image-synthesis disguises below.
- `sources/chunking.py` — cuts a message into large "hyperslices", encrypts each one as a single
  AEAD operation, and splits the result into configurably-sized wire chunks (a plain, variable-
  width sequence number per chunk, followed by a `ChunkEncoding`-transformed payload) with a
  stop-and-wait acknowledgement/retry layer on top. The header is encrypted (and, optionally, also
  disguised — `header_encoding`); the ack is encrypted; each hyperchunk carries a session-scoped ID
  so an ack can be tied back to the transfer it belongs to. See the module's docstring for the full
  design and its open questions.
- `sources/handshake.py` — establishes a session before any data transfer: an unsigned, plain-TOFU
  certificate exchange of fresh per-conversation X25519 keys, an ECDH-derived session key, and the
  derivation (from nothing but each sender's own public transport identifier) of which disguise
  that sender's messages use for the entire conversation. See
  [`docs/handshake.md`](../docs/handshake.md) for the full design and its security properties.
- `sources/corpus.py` — downloads and locally caches the plain-text sentence corpora (English and
  Russian, from [Tatoeba](https://tatoeba.org/en/downloads)) used to train the Markov-chain text
  disguise model. Downloads once per language, on first use; later calls reuse the cached file.
- `sources/data/*.json` — frozen, pre-trained Markov chains (one per language), built from the
  corpora above via `poetry poe train-stego-model` (`scripts/model.py`). Generated, not committed
  — see that file's docstring for why the corpus is capped in size, and regenerate with
  `poetry poe train-stego-model` if it's missing.
- `sources/markov.py` — `MarkovEncoding`, disguising ciphertext as plausible sentences by walking
  the frozen chain above, using a from-scratch, pure-integer arithmetic coder (not a
  general-purpose entropy-coding library -- see the module's docstring for why `constriction` was
  tried and rejected, and
  [design decision #3](../docs/design-decisions.md#3-the-markov-chain-text-disguise-encoding) for
  the full story) so encode/decode agree byte-for-byte on any device, with no floating point or ML
  inference anywhere in that path. `MARKOV_ENG` and `MARKOV_RUS` each have their own
  `ChunkEncoding` identifier, so `unpack_hyperchunk` auto-detects either correctly from the header.
- `sources/arithmetic.py` — the integer arithmetic coder itself (candidate ranges, bit
  cursor/accumulator), factored out of `sources/markov.py` once `sources/synthesis.py` needed the
  identical mechanism for a different kind of candidate.
- `sources/textures.py` — procedural source-texture generators (`value_noise`, `voronoi`,
  `reaction_diffusion`, `attractor`) for image steganography: the image analog of
  `sources/corpus.py`, except self-contained -- no download, no training step, just a size and an
  integer seed, so both ends regenerate an identical texture rather than sharing a file.
- `sources/synthesis.py` — patch-based reversible texture synthesis, adapted from Wu & Wang's
  "Steganography Using Reversible Texture Synthesis" (2015) onto the same arithmetic coder
  `sources/markov.py` uses, rather than that paper's own bespoke (and, for our purposes,
  unnecessary -- see the module's docstring) reversibility bookkeeping. `ImageEncoding` wraps this
  as a `ChunkEncoding` (one PNG-encoded image per hyperchunk, source-texture seed derived from the
  hyperslice's own AEAD nonce) -- four registered instances, one per texture flavor. Visual quality
  is still a prototype-stage tradeoff -- see
  [design decision #4](../docs/design-decisions.md#4-image-steganography-patch-based-texture-synthesis-prototype)
  (locally-stationary textures like `value_noise` hold up well; textures with large-scale
  structure like `voronoi`/`reaction_diffusion` degrade, less so than an earlier naive version but
  still noticeably).

## CI

[`.github/workflows/core.yml`](../.github/workflows/core.yml) runs on every push to `main` and
every pull request touching `core/`: a `lint` job (`poetry poe lint`), and a `test` job (matrix
over Python 3.11/3.12) that trains the stego model and runs `poetry poe test` plus several example
invocations of `poetry poe demo`/`poetry poe demo-handshake` (plain, base64, markov, markov_rus
with a disguised header, an image flavor with a disguised header, and a full handshake) as a live
smoke test, not just the unit suite. The Tatoeba corpus download is cached between runs since it's
an external network dependency otherwise paid on every run.

## Setup

```bash
poetry install --all-extras
```

## Commands

```bash
poetry poe generate           # regenerate sources/proto/*_pb2.py from the .proto schema
poetry poe train-stego-model  # download/cache corpora, (re)train sources/data/markov_*.json
poetry poe demo                 # encrypt + wire-encode a demo message end-to-end, print each step
poetry poe demo-handshake       # run docs/handshake.md's session establishment end to end
poetry poe test                 # run the unit test suite
poetry poe lint                 # flake8 + black --check + mypy
poetry poe format               # black (modifies files)
```

`demo` takes options: `poetry poe demo --mode markov --text "some message" --chunk-size 120`.
`--mode` is any registered `ChunkEncoding` name: `plain`, `base64`, `markov`, `markov_rus` (the two
Markov modes need `sources/data/markov_<language>.json` to exist first -- run
`poetry poe train-stego-model` if it doesn't), or one of `sources/textures.py`'s flavor names
(`value_noise`, `voronoi`, `reaction_diffusion`, `attractor`), which yields exactly one wire chunk
(the whole synthesized image, saved to `--image-path`, default `output.png`) instead of many small
ones -- `chunk_size` defaults to an SMS- or MMS-scale budget depending on which. `--header-mode`
takes the same choices and additionally disguises the header message the same way, e.g.
`poetry poe demo --mode voronoi --header-mode markov`.

`demo-handshake` runs `sources/handshake.py`'s certificate exchange and session-key derivation
between two sender identifiers (`--alice-id`/`--bob-id`, default fake phone numbers), then sends
one real hyperchunk through the derived session key and each side's independently-derived
obfuscation mode -- see [`docs/handshake.md`](../docs/handshake.md) for the design this implements.
